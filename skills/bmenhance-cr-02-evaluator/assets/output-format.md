# CR 评估 — 输出格式模板

本文档定义了代码审查评估文件的标准输出格式。LLM 执行评估后，必须严格按照此模板生成结果文件，无需检索已有评估文件。

---

## 文件命名

`<story-id>-code-review-evaluation-<YYYYMMDD>-round-<m>.md`

---

## 评估文档模板

```markdown
---
Story: <story-id>
Round: <m>
Date: <YYYY-MM-DD>
Model Used: <当前评估模型全名> (<模型标识符>)
Review Source: <被评估的审查结果文件名>
Review Model: <产出审查结果的模型全名> (<模型标识符>)
Type: Code Review Evaluation
---

## 评估总结

对 Story <story-id> 的第 <n> 轮 CR 代码审查结果（<首轮/复审>）进行逐条评估。<审查发现概述>。评估结论如下。
```

## 格式规范

### 优先级定义

- **P0**：安全漏洞、数据完整性风险，必须立即修复
- **P1**：功能缺陷、质量门禁违规，阻塞交付
- **P2**：改进建议、体验优化，纳入 CR TODO 延迟处理
- **P3**：代码风格、命名建议，可选优化

### 评估分析要求

- 必须通过独立代码验证确认问题描述的准确性，引用具体文件和行号
- 严重性判断必须给出理由，尤其在调整原始判断时
- 修复建议的可行性评估应考虑修复成本和风险

### 元信息字段说明

- `Model Used`：当前执行评估的模型名称
- `Review Source`：被评估的审查结果文件名（完整文件名）
- `Review Model`：从被评估审查结果文件头部的 `Model Used` 字段读取

### 审查增强字段说明

审查结果中可能包含以下可选增强字段（由三层并行审查引擎产出），评估时应加以利用：

- `来源`：标识发现由哪个审查层产出
  - `blind`：盲猎手（对抗式审查）
  - `edge`：边界猎手（边缘情况分析）
  - `auditor`：验收审计员（AC 对照审查）
  - 合并来源：如 `blind+edge` 表示两层同时发现了同一问题
- `分类`：四桶分类标签
  - `decision_needed`：需人工裁决的模糊选择
  - `patch`：修复方案明确的代码问题
  - `defer`：既有问题，非本次改动引起

这两个字段为可选，不存在时不影响评估流程。
